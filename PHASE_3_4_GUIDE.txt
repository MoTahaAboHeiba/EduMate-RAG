WHAT YOU'LL FIND IN PHASE 3 & 4
================================

1. RETRIEVAL METRICS
   
   Precision@3 (Target >= 70%)
   - "Of top-3 retrieved documents, how many are relevant?"
   - Values: 0-1 (1 = perfect)
   - What it means: If low, retrieval is not finding right documents
   
   Recall@5 (Target >= 60%)
   - "Of all relevant documents, how many are in top-5?"
   - Values: 0-1 (1 = all relevant docs found)
   - What it means: If low, we're missing relevant documents
   
   MRR (Target >= 75%)
   - Mean Reciprocal Rank
   - "How quickly do we find the first relevant document?"
   - Values: 0-1 (1 = first result is relevant)
   - What it means: If low, relevant docs are ranked low
   
   NDCG@10 (Target >= 70%)
   - Normalized Discounted Cumulative Gain
   - "How good is the overall ranking?"
   - Values: 0-1 (1 = perfect ranking)
   - What it means: Comprehensive ranking quality metric


2. GENERATION METRICS

   Faithfulness (Target >= 95%)
   - "Is the answer grounded in retrieved sources?"
   - Scores: 0-1 (1 = completely grounded, no hallucinations)
   - What it means: If low, LLM is making up answers
   - Fix: Add retrieval validation or stricter prompts
   
   Relevance (Target >= 90%)
   - "Does the answer address the question?"
   - Scores: 0-1 (1 = fully addresses question)
   - What it means: If low, answers are off-topic
   - Fix: Improve LLM prompt or context
   
   Completeness (Target >= 80%)
   - "Is there enough information in the answer?"
   - Scores: 0-1 (1 = complete information)
   - What it means: If low, answers are too brief
   - Fix: Increase max_tokens or improve prompts
   
   Source Accuracy (Target >= 95%)
   - "Are the cited sources actually valid?"
   - Scores: 0-1 (1 = all sources are correct)
   - What it means: If low, citations are wrong
   - Fix: Add source validation


3. PERFORMANCE METRICS

   Avg Latency (Target <= 3000ms)
   - Average response time in milliseconds
   - What it means: How fast the system responds
   - If too high: Optimize API calls or reduce retrieval
   
   P95 Latency (Target <= 5000ms)
   - 95th percentile of response times
   - What it means: How slow 5% of queries are
   - If too high: There are performance bottlenecks
   
   Throughput (Target >= 0.5 q/s)
   - Queries per second the system can handle
   - What it means: System capacity
   - If too low: Cannot handle many concurrent users


INTERPRETING THE RESULTS
========================

SCENARIO 1: All metrics pass (PASS >= 80%)
   Status: System is working well!
   Action: No urgent optimization needed
   Optional: Continue monitoring or fine-tune further

SCENARIO 2: Retrieval metrics fail, generation passes
   Problem: Documents aren't being retrieved correctly
   Causes:
     - Embedding model not capturing question intent
     - Chunk size too large/small
     - Similarity threshold too strict
   Solutions:
     - Try different embedding model
     - Adjust chunk size in pdf_loader.py
     - Increase retrieval top_k in config

SCENARIO 3: Generation metrics fail, retrieval passes
   Problem: LLM is making mistakes
   Causes:
     - LLM hallucinating (making up answers)
     - Prompt not clear enough
     - Context window too small
   Solutions:
     - Add retrieval validation
     - Improve system prompt in rag_chain.py
     - Reduce irrelevant context

SCENARIO 4: Performance is slow
   Problem: System response time too high
   Causes:
     - Groq API is slow
     - Too many documents being retrieved
     - Network latency
   Solutions:
     - Reduce retrieval top_k
     - Cache frequently asked questions
     - Parallelize requests
     - Check network connection

SCENARIO 5: All metrics fail
   Problem: System needs comprehensive overhaul
   Actions:
     - Check if RAG API is working correctly
     - Verify PDFs are loaded in vector store
     - Check if Groq API key is valid
     - Review all configuration settings


WHAT HAPPENS DURING PHASE 3
============================

For each of 85 QA pairs:

1. Question is sent to RAG API
   Question: "What is a data structure?"
   API: http://localhost:8000/api/query
   
2. RAG system retrieves relevant documents
   Result: [doc1, doc2, doc3, doc4, doc5]
   Metric: How many are actually relevant? (Precision)
           Did we find all relevant? (Recall)
   
3. LLM generates answer
   Answer: "A data structure is an organized way to store..."
   Metrics: Is it grounded in sources? (Faithfulness)
            Does it address question? (Relevance)
            Is it complete? (Completeness)
   
4. Metrics are recorded
   For each question, we calculate:
   - Retrieval: Precision@3, Recall@5, MRR, NDCG
   - Generation: Faithfulness, Relevance, Completeness, Source Accuracy
   - Performance: Latency (response time)
   
5. Results saved
   Results stored for later analysis

KEY INSIGHTS TO LOOK FOR
=========================

1. Category-specific weaknesses
   - Is one subject (OS, ML, OOP) performing worse?
   - If yes: Those PDFs might need better indexing

2. Latency patterns
   - Some queries much slower than others?
   - Might indicate chunking or retrieval issues

3. Hallucination patterns
   - Which questions produce hallucinations?
   - Might indicate insufficient context

4. Consistency
   - Do similar questions get similar scores?
   - If not: System is inconsistent

5. Correlation
   - Does low retrieval cause low generation?
   - Expected: Yes, good retrieval enables good generation


HOW TO OPTIMIZE AFTER SEEING RESULTS
=====================================

If Precision is low:
   1. Check pdf_loader.py - try smaller chunk_size
   2. Try different embedding model
   3. Increase retrieval_top_k in config

If Recall is low:
   1. Increase retrieval_top_k in config
   2. Try larger chunk_size
   3. Check if PDFs are fully indexed

If Faithfulness is low (hallucinations):
   1. Add retrieval validation in rag_chain.py
   2. Modify LLM prompt to be stricter
   3. Reduce temperature in config

If Latency is high:
   1. Reduce retrieval_top_k
   2. Check Groq API status
   3. Optimize chunking strategy

If everything is bad:
   1. Verify RAG server is running correctly
   2. Check Groq API key is valid
   3. Verify PDFs are loaded in vector database
   4. Check network connection

TROUBLESHOOTING PHASE 3 & 4
============================

Phase 3 fails with "Cannot connect to API":
   -> Make sure RAG server is running
   -> Run: python src/api/main.py in separate terminal
   -> Verify: curl http://localhost:8000/health

Phase 3 is very slow:
   -> Normal for first run (LLM loads on first use)
   -> Subsequent runs should be faster
   -> Check Groq API status

Phase 3 returns 0 results:
   -> Check if RAG API is returning valid responses
   -> Check: curl -X POST http://localhost:8000/api/query -H "Content-Type: application/json" -d '{"question":"What is data structure?"}'

Phase 4 fails to find Phase 3 results:
   -> Make sure Phase 3 completed successfully
   -> Check if files were saved in evaluation/results/
   -> Re-run Phase 3

HTML report looks broken:
   -> Open in different browser
   -> Check if analysis_*.json was created
   -> Re-run Phase 4
